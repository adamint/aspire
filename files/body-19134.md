## Description

An agent that wants to restart your app today shells out to `aspire run` in a terminal. That process is invisible to VS Code: it does not attach the debugger, it does not show up in the Aspire panel, and the editor cannot shut it down cleanly. Worse, if you already had an AppHost paused on a breakpoint, the agent has just started a second one on top of it.

This adds two Language Model tools so agents drive the editor's own AppHost lifecycle instead:

| Tool | Reference in chat | What it does |
|------|-------------------|--------------|
| `aspire_apphost_start` | `#aspireStartAppHost` | Starts an AppHost already in the workspace, in `run` or `debug` mode |
| `aspire_apphost_stop` | `#aspireStopAppHost` | Stops an AppHost this editor started |

Both tools go through the same `AppHostLaunchService` path as Run/Debug, so an agent-started AppHost is a real editor session — debugger attached, visible in the Aspire panel, stoppable, and torn down with its child resources.

### What the tools deliberately will not do

The interesting design work here is in the refusals. A model supplies the path, so the tool treats its input as untrusted:

- **No guessing.** The AppHost path is required and must be workspace-relative. Missing, ambiguous, or outside-the-workspace input fails (`pathNotFound`, `pathAmbiguous`, `pathOutsideWorkspace`, `pathEscapesWorkspace`) rather than picking an AppHost for you.
- **No duplicate launches.** Work is serialized per AppHost against the lock the editor's own Run/Debug commands use, and re-validated inside it. A second start returns `alreadyStarting` / `alreadyRunning`.
- **No misleading stop result during start.** If a start is reserved but its debug session is not observable yet, stop returns `alreadyStarting` / `editor`, not `notRunning`.
- **No adopting or killing what the editor does not own.** An AppHost you started in a terminal is reported back as `notEditorOwned`, never terminated.
- **No running arbitrary commands.** The Aspire command is pinned to `run`; `mode` only chooses whether the debugger attaches.
- **No CLI fallback and no public extension API.** The tools are the only surface, so there is no second path with weaker checks.
- **Trusted workspaces only** (`when: "isWorkspaceTrusted"`), and every call is confirmed by the user.
- **Nothing sensitive reaches the transcript.** Results are a fixed, bounded shape; error details are logged, not returned.

Confirmation text is also treated as attacker-controlled: model-supplied paths are sanitized before rendering, including Unicode format characters and Markdown-sensitive characters such as `&`, so a bidi override, zero-width character, or CommonMark entity cannot disguise the path being approved. A path that cannot be resolved into the workspace is described with a fixed placeholder instead of echoing the model's prose into the dialog.

The E2E test drives the real tools through `vscode.lm.invokeTool` against a real AppHost, answers the modals, and asserts on processes and debug sessions. Its artifact:

- Two concurrent `start` calls → exactly one `started`, one `alreadyStarting`, one process, one debug session
- `start` again while running → `alreadyRunning`, `requestedMode: run` but `effectiveMode: debug` (a start cannot silently convert a debug session into a run session), original process untouched
- `stop` → `stopped`, no debug sessions and no AppHost processes remain
- `stop` again → `notRunning`, `controller: none`

The E2E spec is now included in the explicit extension E2E matrix on both OS rows. Locally, the spec body passed; the ExTester root `after all` timeout also reproduces on pre-existing matrix specs and matches the known #18098 harness flake, not this spec. Mutating the lifecycle reservation check made the spec fail with the duplicate-launch behavior it is supposed to catch.
